\# Observability / Tracing（可观测性与追踪）



\## 1. Observability、Tracing、Log 的区别



\- \*\*Observability（可观测性）\*\*：通过日志、追踪、指标等数据理解系统内部发生了什么，用于定位异常、分析性能问题并找出瓶颈。

\- \*\*Tracing（追踪）\*\*：将一个任务中的多个执行步骤串联起来，查看它们的先后顺序、调用关系和结果。

\- \*\*Log（日志）\*\*：记录任务执行过程中每一个事件具体发生了什么。



> 三者关系：Log 和 Tracing 是数据来源，Observability 是利用这些数据（以及指标）理解系统的整体能力。



\## 2. Trace 与 Span 的关系



\- \*\*Trace\*\*：一次任务追踪的完整记录。

\- \*\*Span\*\*：Trace 内部的一个执行单元，记录该单元的执行情况，包括开始时间、结束时间、耗时和状态。



一个 Trace 由多个 Span 组成。



\## 3. 为什么失败步骤也必须记录



失败步骤不一定导致任务失败，任务成功也不代表每个步骤都成功。因此，记录失败步骤有两方面价值：



\- 作为任务失败时排查原因的定位依据。

\- 作为性能分析和优化 Agent 瓶颈的参考。



\## 4. 单步骤耗时与整个任务耗时的区别



\- \*\*单步骤耗时\*\*：Span 记录的某个执行单元从开始到结束所花费的时间。

\- \*\*整个任务耗时\*\*：从任务开始到任务结束的总时长。



如果步骤存在并行执行、等待或重叠，总耗时不一定等于各步骤耗时之和。



单步骤耗时的差异可以结合指标阈值或基线来识别异常，从而定位异常发生的具体位置。



\## 5. 当前实验的局限：Trace 仅存在内存中，未持久化



当前 Trace 只存在于 Python 的内存字典中，不会自动持久化，程序退出后就无法再次查看。如果需要长期查询，就需要接入持久化存储机制，例如：



\- 写入本地文件（JSON / JSONL）

\- 写入数据库

\- 接入专用的 Tracing 平台
