\# Tool Calling：工具调用



\## 1. 一句话定义



Tool Calling 是一种机制：模型提出结构化的工具调用请求，由外部程序根据请求执行相应工具，并将执行结果返回模型。



模型提出请求，不等于工具已经执行，更不等于任务已经成功。



\## 2. 为什么 Agent 需要 Tool Calling？



LLM 可以理解指令、分析信息并生成行动请求，但它不会仅凭这些能力就自动获得本地文件、数据库、浏览器或硬件的访问权限。



Tool Calling 让模型能够请求外部程序执行操作，从而将模型的生成能力连接到真实的执行环境。



典型用途：



\- 读取和搜索文件

\- 查询数据库

\- 调用 HTTP API

\- 执行测试

\- 搜索 GitHub 项目

\- 与经过授权的外部设备交互



\## 3. 三个核心角色



\### LLM



负责理解任务、处理上下文，并生成回答或下一步行动请求。



\### Agent Runtime



负责组织运行流程，解析模型输出，协调工具调用，管理状态，并处理继续执行、结束和异常等情况。



\### Tool



负责提供实际执行能力，例如读取文件、调用 API 或运行受限的代码。



\## 4. 执行流程



用户任务

→ LLM 生成回答或工具调用请求

→ Runtime 检查请求

→ 执行 Tool

→ 得到成功结果或错误

→ 将结果交还模型

→ 模型决定下一步

→ 检查是否满足结束条件。



\## 5. 一个重要区别



Tool Calling 不等于模型直接执行代码。



例如，模型返回一个读取文件的请求时，Runtime 仍需要通过已经注册的工具执行文件读取。



工具能访问哪些文件、是否允许修改文件，以及能执行哪些操作，取决于工具实现和权限设置。



\## 6. 工具执行失败怎么办？



不能只依靠 Prompt 要求模型自行纠错。



可靠的系统应该考虑：



1\. 明确记录成功状态与失败状态。

2\. 将错误信息以可识别的形式返回模型。

3\. 根据错误类型决定是否重试。

4\. 限制最大重试次数，防止无限循环。

5\. 在执行敏感操作前检查权限与参数。

6\. 对关键结果进行独立验证。

7\. 无法确认成功时停止执行，并如实报告。



模型可以参与错误恢复，但程序也必须设置相应约束。



\## 7. 企业生产环境中的问题



\- 工具参数可能不合法。

\- 工具可能超时或不可用。

\- 模型可能误解工具返回结果。

\- 模型可能在工具失败后仍然声称成功。

\- 未经授权的调用可能产生安全风险。

\- 多次重试可能增加时间和费用。

\- 工具返回内容可能包含不可信信息。



这些问题需要通过参数校验、权限控制、错误处理、调用限制、日志和结果验证等机制共同解决。



\## 8. 我的理解



LLM 是决策能力来源，Runtime 负责调度与控制，Tool 提供实际执行能力。



模型提出调用请求后，Runtime 才能根据规则决定如何执行。工具返回的结果是模型下一步决策的依据，但模型不一定能够正确解释结果。



因此，任务完成不能只依赖模型的自我判断，还应在需要时使用程序验证。
