# Runtime Safety: Tool Registry, Validation and Execution Limits

## 1. 一句话定义

Runtime Safety 是指通过工具注册、参数校验、权限控制、异常处理和执行限制等机制，约束 Agent 的运行行为，降低错误执行和资源浪费的风险。

Runtime 不只是调用工具的执行层，也是连接 LLM 的行动请求与实际工具执行的控制层。

## 2. LLM、Runtime 与 Tool 的职责

在当前的最小 Agent 实验中，三者的职责如下：

* **LLM**：理解用户任务，根据工具描述决定下一步行动，并在需要时生成结构化的工具调用请求。
* **Runtime**：接收模型响应，检查工具名称和参数，调度工具执行，将执行结果交还模型，并控制整体执行流程。
* **Tool**：执行实际操作，例如计算、查询数据或调用外部 API。

需要注意：LLM 发出工具调用请求，并不意味着它直接执行了本地 Python 函数。实际执行由 Runtime 完成。

## 3. Tool Registry

Tool Registry 将工具名称映射到实际可调用的函数或处理器。

例如：

```python
TOOL_REGISTRY = {
    "divide": divide,
}
```

主要作用：

* 根据模型提出的工具名称查找实际工具。
* 限制通过当前调度机制可以访问的工具集合。
* 为后续权限控制、工具管理和审计提供入口。

注意：注册表不等于完整的安全机制。已注册工具仍需要权限检查、参数校验和业务约束。

## 4. 参数校验

参数校验至少应考虑：

1. 工具名称是否存在。
2. 参数是否为预期的数据结构。
3. 必填字段是否缺失。
4. 参数类型是否正确。
5. 参数值是否满足范围与业务约束。
6. 调用者是否有权限执行相应操作。

以 `divide(a, b)` 为例：

* `{"a": 10, "b": 2}`：符合基本输入要求。
* `{"a": 10}`：缺少必填参数 `b`。
* `{"a": "hello", "b": 2}`：参数 `a` 的类型不符合要求。
* `{"a": 10, "b": 0}`：违反除数不能为零的约束。

参数通过校验也不保证任务最终成功，执行结果仍需检查。

当前实验通过工具描述告诉模型参数结构，并在 Runtime 中执行基本的参数检查。工具描述和运行时校验是两个不同层次，不能只依赖模型遵守参数规范。

## 5. 异常处理

工具执行可能失败，例如：

* 参数错误。
* 网络超时。
* 外部服务不可用。
* 权限不足。
* 业务规则拒绝请求。

Runtime 应将错误转化为可处理的结果，并根据错误类型决定重试、修正请求、转交人工或停止任务。

例如，当前实验将工具执行结果组织为类似下面的结构：

```json
{
  "ok": false,
  "error": "除数不能为零"
}
```

随后 Runtime 将结果通过对应的 `tool_call_id` 交还模型。

工具失败不必然意味着整个 Agent 流程失败。只要错误被正确捕获、结果被正确回传，模型就可以根据错误信息解释失败原因。

但是，权限拒绝、不可恢复的业务错误和安全风险不能一律通过重试解决。

## 6. 执行限制

常见的执行限制包括：

* 最大模型请求轮数。
* 工具调用超时。
* 有限次数的重试。
* Token 或费用预算。
* 权限与审批检查。
* 任务停止条件。

不能无限重试所有错误。对于参数缺失、权限不足等不能通过重复请求解决的问题，通常应该修正请求或停止执行。

### 当前实验中的限制

当前 Python 程序设置了：

* `max_steps=5`：限制一次任务循环中最多发起五轮模型请求。
* `timeout=30.0`：为单次 SDK 请求设置超时时间。
* `max_retries=1`：配置 SDK 的有限重试行为。

需要注意：

* `max_steps` 限制的是模型请求轮数，不是所有工具调用次数的独立上限。
* 一轮模型响应可能包含多个工具调用，因此还需要考虑工具调用数量限制。
* SDK 的请求重试与 Agent 自身决定重新调用工具，是两种不同的机制。
* 当前实验尚未实现完整的费用预算、权限审批和任务取消系统。

## 7. 三种不同的状态

理解 Agent 执行过程时，需要区分三个状态：

1. **模型已提出工具调用请求**：LLM 返回了 `tool_calls`，请求 Runtime 执行指定工具。
2. **工具执行成功或失败**：Runtime 实际执行工具，并获得结果或错误。
3. **任务完成**：最终结果经过必要检查，符合用户的要求。

这三个状态不能混为一谈。

模型提出了工具调用，不代表工具已经执行成功；工具执行成功，也不代表整个任务已经完成。

## 8. 实际实验记录：DeepSeek Tool Calling

实验文件：

`04-labs/02_deepseek_tool_calling.py`

实验使用 DeepSeek API、Python SDK 和本地 `divide` 工具，验证了模型调用工具、Runtime 执行工具以及工具结果回传的基本流程。

### 测试 A：正常工具调用

用户输入：

`请使用工具计算 10 除以 2。`

实际观察：

* Runtime 请求 DeepSeek。
* DeepSeek 返回 `divide` 工具调用。
* 本地 Python 函数执行成功，返回 `5.0`。
* Runtime 发起第二轮模型请求。
* 模型根据工具结果返回最终回答。

结果：通过。

### 测试 B：工具执行失败

用户输入：

`请使用工具计算 10 除以 0。`

实际观察：

* DeepSeek 返回 `divide` 工具调用。
* 本地工具因除数为零而执行失败，产生 `ValueError`。
* Runtime 捕获异常，将错误结果回传模型。
* Runtime 发起第二轮模型请求。
* 模型说明计算失败，没有将工具错误当成成功结果。

结果：通过。

### 测试 C：不需要工具的普通问题

用户输入：

`请用一句话解释什么是 Python，不要进行任何计算。`

实际观察：

* Runtime 请求 DeepSeek。
* 模型直接返回最终回答。
* 没有发生 `divide` 工具调用。

结果：通过。

### 实验结论

三个测试分别验证了：

* 需要工具时，模型可以提出工具调用请求。
* 工具执行失败时，Runtime 可以捕获错误并将结果交还模型。
* 不需要工具时，模型可以直接回答。

因此，当前实验已经跑通最小 Tool Calling 闭环，但这并不意味着系统已经达到生产级安全标准。

## 9. API Key 与 Git 安全

当前实验通过项目根目录中的 `.env` 文件保存本地 API Key，并通过 Python 环境变量读取密钥。

安全规则：

* 不在 Python 源码中硬编码 API Key。
* `.gitignore` 中包含 `.env` 忽略规则。
* 不将 `.env` 文件提交到 GitHub。
* 不在公开日志、截图或聊天中暴露密钥。

需要注意：`.env` 是本地明文文件，不是加密保险箱；Git 忽略规则也不会自动取消一个已经被 Git 跟踪的文件。

提交代码之前，应检查：

```bat
git check-ignore .env
git ls-files .env
```

预期情况：

* 第一条命令显示 `.env`，表示忽略规则生效。
* 第二条命令没有输出，表示 `.env` 没有被 Git 跟踪。

如果密钥意外泄露，应及时撤销旧密钥并重新生成。

## 10. 当前实现的局限

当前实现是一个学习用的最小 Runtime，不是生产级 Agent。

后续仍需要研究：

* 更严格的参数 Schema 校验。
* 工具权限与最小权限原则。
* 高风险工具的人工审批。
* 网络错误、业务错误与权限错误的分类。
* 有区别的重试策略。
* 最大工具调用次数、超时、费用预算与任务取消。
* 工具调用日志、执行追踪与审计。
* 最终结果的独立验证。
* 多工具调用和更复杂的状态管理。

后续学习应通过逐项实现和测试这些能力，而不是一次性引入所有机制。
